# NANE — المرحلة الرابعة: واجهة المتصفح

## الحالة

**اكتمل تنفيذ الواجهة وربطها بواجهات الخادم واختبار عقدها آليًا.** لا يعني ذلك أن Safari 9 أو Android قد اختُبرا على أجهزة فعلية؛ هذا اختبار قبول مستقل ضمن المرحلة الخامسة.

## الشاشات

- **الدخول والغرفة:** إنشاء الغرفة والانضمام إليها، رمز دعوة قابل للنسخ، قائمة اللاعبين، الاتصال والاستعداد.
- **الملف الشخصي:** تحميل الأسئلة من `GET /profile`، عرض الأسئلة حسب المجموعة، حفظ جزئي تلقائي عبر `POST /profile`، ومؤشر تقدم حتى 21 إجابة.
- **ساحة المباراة:** اسم المرحلة ورقم الجولة والوقت المتبقي ولوحة ترتيب مباشرة.
- **الكشف والختام:** عرض نتيجة المهمة بعد أن يكشفها الخادم، ثم شاشة الترتيب النهائي وإمكانية العودة إلى الغرفة.

## ربط المراحل

| مرحلة الخادم | سلوك المتصفح |
|---|---|
| `knowledge` | يعرض السؤال وخياراته للاعبين المخمّنين؛ صاحب الملف ينتظر الكشف. |
| `mystery` | يعرض القصة والتلميحات التي كشفها الخادم فقط، ويسمح بتخمين صاحب الرسالة. |
| `player_question` | المجيب السري وحده يرى خيارات الإجابة؛ بعد إرساله تظهر خيارات تخمين الإجابة للآخرين. |
| `live_choice` | يحفظ إجابة كل لاعب سرًا، ثم يعرض الإجابات المجهولة واحدة تلو الأخرى ويطلب تخمين صاحبها. |
| `finale` | يعرض اللغز المركب ويطلب اختيار صاحب الحقائق. |

كل إرسال للمباراة يضم `task_sequence` الذي أعاده الخادم. بعد إعادة التحميل أو عودة الاتصال، تستعيد الواجهة المهمة الحالية من `GET /match` بدل الاعتماد على حالة JavaScript المحلية.

## تنظيم العميل والتوافق

- التطبيق في `web/js/app.js` يستخدم وحدات صغيرة ووظائف صريحة: طلبات HTTP، حالة الغرفة، الملف الشخصي، عرض المباراة، وإرسال الاختيارات.
- الاتصال عبر `XMLHttpRequest`، مع صياغة JavaScript محافظة ومتوافقة مع ES5؛ لا يستخدم `fetch` أو `Promise` أو arrow functions.
- التصميم RTL، مع نقاط استجابة للهواتف، أزرار كبيرة للمس، ولا يعتمد على CSS Grid أو خاصية flex gap.
- لا تستخدم الواجهة `localStorage` لتخزين إجابات الملف أو أسرار المباراة. قاعدة البيانات والخادم هما مصدر الحقيقة.
- يتم إنشاء نصوص المستخدم والمحتوى عبر عقد النص في DOM، لا عبر إدراج HTML خام.

## الاختبارات الآلية

`tests/test_ui_contract.py` يتحقق من نقاط تركيب الشاشات، واتجاه RTL، ومسارات الملف والمباراة، وإرسال رقم الجولة، وملاءمة صياغة العميل لـES5، ومحددات التصميم للشاشات الضيقة. ويشغّل `run_tests.sh` فحص صياغة JavaScript بواسطة Node إن كان متاحًا، بالإضافة إلى اختبارات Python وHTTP.

يوجد كذلك `tests/test_ui_runtime.js`، وهو اختبار smoke مستقل بلا اعتماديات يحاكي DOM وXHR ويشغّل العميل الفعلي عبر تعبئة الملف، الاستعداد، بدء المباراة، إرسال تخمين برقم المهمة، واستلام الكشف. يشغّله `run_tests.sh` وGitHub Actions.\n\nهذه الاختبارات تثبت سلامة البنية والعقود ومسار العميل الأساسي، لكنها ليست اختبار متصفح رسومي ولا محاكاة دقيقة لـSafari 9.

## اختبار القبول اليدوي المطلوب

1. على iPhone 4S وSafari 9.3.6: فتح رابط HTTPS، إنشاء/الانضمام إلى غرفة، قراءة الصفحة بعرض 320px، واختيار كل إجابات الملف وحفظها.
2. على Android: اختبار الانضمام، التحديث أثناء الانتظار، الاستعداد، وتزامن ظهور المباراة.
3. تشغيل مباراة من ثلاثة لاعبين ثم أربعة، وتجربة كل نوع مرحلة والإجابة والتخمين والكشف والنتيجة.
4. تحديث المتصفح أو قطع الاتصال وإعادته أثناء كل مرحلة؛ يجب استعادة نفس المهمة وعدم قبول اختيار قديم.
5. مراقبة عدم وجود تمرير أفقي أو عناصر لمس صغيرة، والتأكد من بقاء النصوص العربية واضحة.

## حدود المرحلة

لم أجرِ اختبارًا فعليًا على iPhone أو Android من داخل بيئة التطوير. لا تُعتمد المرحلة ميدانيًا قبل تنفيذ الاختبار اليدوي أعلاه وتسجيل أي أخطاء وإصلاحها.
